# ADR-004: Отпечаток v1 и таблица issue_hash

**Status:** Accepted
**Date:** 2026-11-04
**Feature:** error-ingest
**Author:** 10x-Team (Architect + Staff Engineer)

## Context
Качество группировки — главное, что отличает полезный трекер от свалки. Номера строк и хеши
сборок меняются каждый релиз. Алгоритм наверняка будет улучшаться (шаг 3 — карты исходников),
а пользователям понадобится вручную склеивать проблемы.

## Decision
- Отпечаток: свой `fingerprint` SDK (с `{{ default }}`) → иначе тип + кадры своего кода
  (module/нормализованный файл + функция, без строк и колонок) → иначе тип + нормализованный
  текст. `sha256` → 32 hex. Подробности — спека, раздел 3.
- Связь «отпечаток → проблема» — отдельная таблица `issue_hash (project_id, hash, version,
  issue_id)`, а не колонка в `issue`. Новые проблемы заводятся в транзакции; гонку копий
  разрешает `on conflict do nothing` по PK `issue_hash`.

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| Колонка `hash` с unique в `issue` | один upsert | нельзя склеить проблемы, нельзя сменить алгоритм без «новых» проблем | закрывает будущее |
| Отпечаток по номерам строк | точнее различает | каждый релиз — новые проблемы | шум |

## Consequences
### Positive
- Склейка проблем и смена алгоритма (v2) без потери истории.
### Negative
- Лишний поиск по `issue_hash` на пачку (один запрос).
### Risks
- До шага 3 сжатый код даёт разные имена функций между сборками → дробление проблем.

## Dependencies
- Шаг 3 добавит v2 по исходному коду; старые хеши продолжат вести к тем же проблемам.
