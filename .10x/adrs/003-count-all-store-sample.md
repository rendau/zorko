# ADR-003: «Считать всё, хранить часть» — event_stat + event, счётчик минуты в Postgres

**Status:** Accepted
**Date:** 2026-11-04
**Feature:** error-ingest
**Author:** 10x-Team (Architect + Staff Engineer + DBA)

## Context
Плохой релиз даёт миллионы одинаковых ошибок. Пользователь выбрал: счётчики и графики точные,
полные записи — не больше 100 в минуту на проблему; хранение 30 дней. Копий обработки несколько,
лимит должен быть общим.

## Decision
- ClickHouse: `event_stat` — каждое событие коротко (для графиков, уникальных людей, тегов);
  `event` — полные записи, только разрешённые. Обе — `ReplacingMergeTree`, TTL 30 дней по
  `received_at`.
- Разрешение считает Postgres: в `issue` поля `stored_minute`, `stored_in_minute`; один
  `UPDATE … RETURNING` с блокировкой строк на пачку увеличивает `times_seen` и выдаёт, сколько
  полных записей можно сохранить в текущую минуту (по времени обработки).
- При ошибке ClickHouse повторяется только вставка, без повторного обновления Postgres.

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| Лимит на проект с отбросом (как Sentry) | просто | счётчики занижены | не выбор пользователя |
| Хранить всё | ничего не теряем | диск и скорость поиска страдают | не выбор пользователя |
| Лимит в памяти каждой копии | без запроса в БД | неточный (×число копий) | запрос всё равно нужен для счётчиков |
| Счётчик в Redis | быстро | ещё одна зависимость | Postgres уже обновляется той же пачкой |

## Consequences
### Positive
- Точные счётчики и графики при любом наплыве; ограниченный рост `event`.
### Negative
- Две таблицы с дублированием ключевых полей; уникальные пользователи — только из `event_stat`.
### Risks
- Горячая проблема → конкуренция за строку `issue` между копиями: одна строка на пачку,
  а не на событие, этого достаточно; при необходимости — шардирование счётчика.

## Dependencies
- Шаг 2 строит графики и распределения тегов по `event_stat`, подробности — по `event`.
