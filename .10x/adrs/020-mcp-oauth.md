# ADR-020: MCP-сервер для AI-агентов — только чтение, вход по OAuth через страницу согласия

**Status:** Accepted
**Date:** 2026-11-13
**Feature:** mcp
**Author:** 10x-Team (Architect + Security)

## Context
Нужно, чтобы AI-агент (приложения Claude, Claude Code) мог сам смотреть ошибки в zorko: какие
проблемы в проекте, стек, у кого и после каких действий. Образец — встроенный MCP-сервер kusec с
входом по OAuth: человек вписывает в клиент только адрес, клиент открывает страницу согласия,
человек входит и разрешает.

Отличия zorko от kusec:
- три способа входа в интерфейс (ADR-019), причём при `oidc` и `proxy` своего `JWT_SECRET` нет;
- своих API-ключей у людей нет (токены CI — для заливки карт, не для чтения);
- API проблем и событий только читает, менять в zorko агенту нечего;
- копий сервиса несколько, они перезапускаются при выкате.

## Decision
1. **Встроенный MCP на своём порту** (`MCP_ENABLED`, `MCP_PORT`, 5060): транспортный слой
   `internal/handler/mcp` поверх тех же usecase, что gRPC, — права и видимость проектов проверяет
   usecase, второй реализации доступа нет. Библиотека — `modelcontextprotocol/go-sdk`.
2. **Только чтение.** 12 инструментов: `list_project`; `list_issue`, `get_issue`, `get_issue_stat`,
   `get_issue_tags`; `list_event`, `get_event`; `list_tag_key`, `list_tag_value`; `list_replay`,
   `get_replay`, `list_issue_replay`. Управление (проекты, ключи, люди, токены CI) — только в
   интерфейсе. Событие отдаётся разобранным и урезанным (до 50 кадров стека, строки кода только у
   кадров приложения, 30 последних действий, значения до 2000 символов): исходный JSON бывает до
   мегабайта. Секреты проекта (заголовок скачивания карт с сайта) в ответы не попадают.
3. **Без сессий на сервере** (`Stateless` в go-sdk, ответы обычным JSON): каждый запрос
   самодостаточен и проверяется по своему токену. Копий сколько угодно, привязка клиента к копии не
   нужна, перезапуск подключения не рвёт. У kusec сессии есть ради реестра значений секретов — в
   zorko хранить между вызовами нечего.
4. **Вход — только OAuth 2.1**, схема kusec:
   - на MCP-порту — описание ресурса и сервера (`/.well-known/oauth-protected-resource`,
     `/.well-known/oauth-authorization-server`), `/register`, `/token`, `/revoke`; ответ 401 несёт
     `WWW-Authenticate: Bearer resource_metadata=…`;
   - страница согласия — `/oauth/authorize` интерфейса; решение человека уходит в API
     (`OAuthService`, gRPC) с его обычным входом. Поэтому согласие работает при любом `AUTH_MODE`:
     человек входит так же, как всегда;
   - регистрация клиента открыта (так требует протокол), защита — список разрешённых адресов
     возврата `MCP_OAUTH_REDIRECT_URIS`; в базу регистрация не пишет: `client_id` — подписанные
     данные клиента;
   - обязателен PKCE (S256); код живёт 2 минуты, access-токен — `MCP_OAUTH_ACCESS_TTL` (1 ч),
     refresh — `MCP_OAUTH_REFRESH_TTL` (30 дней), при обновлении выдаётся новая пара; в базе
     (`oauth_token`) только sha256.
5. **Подключение = человек.** Запись `oauth_grant` привязана к `usr.id`; на каждый запрос человек
   перечитывается из базы: отключили в «Людях» или сняли проект — действует сразу. Основной API
   токены MCP (`zko_…`) не принимает.
6. **Ключ подписи `client_id`** — `MCP_OAUTH_SECRET`, а если он пуст — `JWT_SECRET`. При `oidc` и
   `proxy` своего секрета нет, поэтому там `MCP_OAUTH_SECRET` обязателен.
7. **Обмен токена без общей транзакции слоёв:** код и refresh-токен гасятся в репозитории одной
   транзакцией с выдачей новых (`ExchangeToken`). Проверки (клиент, PKCE, человек активен) идут до
   неё, так что неудачная проверка токен не сжигает, а из двух одновременных обменов выигрывает один.
8. **Наблюдаемость:** вызовы инструментов — в `request_total` / `response_duration_seconds` с
   `protocol="mcp"`, `method` — имя инструмента; каждый запрос порта — строкой `mcp: request`
   (вид учётных данных, адрес клиента, без самих токенов).

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| API-ключи людей, как `ksk_` в kusec | проще для скриптов | ещё одна сущность, ключ лежит в конфиге агента | пользователь просил OAuth; ключей у людей в zorko нет |
| Отдавать агенту токен провайдера (`oidc`) | нет своего OAuth | у `local` и `proxy` не работает; токен провайдера даёт больше, чем чтение zorko | один способ на все режимы |
| Сессии MCP на сервере, как в kusec | привычно | привязка к копии, обрыв при выкате | хранить между вызовами нечего |
| Инструменты записи (проекты, ключи) | агент настраивает сам | риск при ошибке агента, польза мала | отложено: чтение закрывает задачу |
| Клиенты OAuth в базе | отзыв клиента по одному | открытый адрес пишет в базу — мусор и нагрузка | подпись вместо хранения |
| Исходный JSON события целиком | ничего не теряется | до мегабайта в ответ агенту | урезанный разбор, полное — по ссылке в интерфейсе |

## Consequences
### Positive
- Клиенту нужен один адрес; в конфиге агента нет ни ключей, ни токенов.
- Права агента — ровно права человека, который его подключил, и только на чтение.
- Отключение — одной кнопкой в интерфейсе («AI-агенты»), действует сразу.
### Negative
- Ещё один порт наружу: коннекторы claude.ai ходят с серверов Anthropic, порт должен быть доступен
  из интернета.
- Смена `MCP_OAUTH_SECRET` (или `JWT_SECRET`, если он используется) отключает всех клиентов —
  подключаться заново.
- При `oidc` и `proxy` флаг админа в `usr` обновляется при входе человека в интерфейс: роль, снятая
  у провайдера, остаётся у подключения до его следующего входа. Доступ тот же, что на чтение у
  интерфейса, инструментов записи нет.
### Risks
- **В ответах есть личные данные** посетителей сайтов (почта, IP, адреса страниц) — те же, что
  видит человек в интерфейсе. Они уходят в клиент агента; подключать стоит только тем клиентам,
  которым это допустимо.
- **`proxy`:** MCP-порт публикуется отдельно от API и мимо проверки входа шлюза (шлюз не знает
  токенов `zko_`); свои токены порт проверяет сам. API по-прежнему доступен только через шлюз.

## Dependencies
- ADR-019 (способы входа): согласие идёт под обычным входом человека.
- ADR-005 (`JWT_SECRET`) — запасной ключ подписи клиентов при `AUTH_MODE=local`.
