# ADR-019: Три способа входа — свои учётки, OpenID-провайдер, доверенный шлюз

**Status:** Accepted
**Date:** 2026-11-09
**Feature:** auth
**Author:** 10x-Team (Architect + Security)

## Context
Вход в интерфейс был только свой (ADR-005): логины и пароли в базе zorko. Нужно, чтобы при установке
можно было выбрать:
- свои учётки — как раньше;
- обычный внешний вход через OpenID Connect (Keycloak, id.mdev.kz и т.п.);
- вход через шлюз ruto, который сам проводит вход, держит токены в httpOnly-куках и передаёт
  бэкенду `Authorization: Bearer`. При этом zorko не должен знать, что это ruto.

Права в zorko держатся на записи человека в `usr` (id, флаг админа, видимые проекты), поэтому
внешнего человека всё равно нужно связать с записью.

## Decision
1. **`AUTH_MODE`** — `local` | `oidc` | `proxy`, один на установку. Модуль
   `internal/service/authn` превращает токен из запроса в сессию (`Session{Id, Admin}`), остальной
   код не меняется:
   - `local` — свой токен (HS256, `JWT_SECRET`), как в ADR-005;
   - `oidc` — подпись по ключам провайдера (`go-oidc`: discovery по `OIDC_ISSUER`, ключи
     перечитываются при смене `kid`), `iss`, `exp`, при `OIDC_AUDIENCE` — `aud`. Discovery — при
     первом токене: недоступный провайдер не мешает старту, но запросы получают 503, а не 401;
   - `proxy` — claims читаются без проверки подписи и срока: их проверил шлюз. Шлюз задаётся
     только адресами `AUTH_PROXY_LOGIN_URL` / `REFRESH_URL` / `LOGOUT_URL` (`{url}` — адрес
     возврата), слова ruto в коде нет.
2. **Человек по токену.** Ключ — claim `sub` (колонка `usr.ext_sub`, уникальна среди непустых):
   найден — логин, имя и флаг админа подтягиваются из токена; не найден, но есть непривязанная
   учётка с тем же логином — привязывается (админ завёл человека заранее и выдал проекты; так же
   переезжают учётки, заведённые до включения внешнего входа); иначе заводится. Логин занят
   человеком с другим `sub` — новому дописывается суффикс от хеша `sub`. «sub → человек» помнится
   30 с; отключённый в «Людях» получает `usr_disabled` (403).
3. **Админ — роль из токена** (`AUTH_ADMIN_ROLE`), по правилу ruto: `клиент:роль` — только в
   `resource_access.<клиент>.roles`, просто `роль` — в `roles`, `role`, `realm_access.roles` и у
   любого клиента. `AUTH_ROLES_CLAIM` — явный путь через точку (`groups`, ключи объекта как у
   Zitadel, имя с точками целиком как у Auth0). Логин — `AUTH_USERNAME_CLAIM`, по умолчанию
   `preferred_username`, затем `email`.
4. **Видимые проекты — в zorko.** Провайдер про проекты не знает. Пустой `project_ids` теперь
   значит «ни одного», «все проекты» — отдельная `usr.all_projects`. Миграция 000004 ставит её
   тем, у кого список был пуст, — у существующих людей доступ не меняется. Новый внешний человек
   не видит ничего, пока админ не выдаст проекты.
5. **Внешний вход выключает своё:** `/usr/login`, `/usr/token/refresh`, правка профиля —
   `auth_external`; первого админа без входа нет (`BootstrapStatus` всегда false); админ не
   задаёт пароль и флаг админа, логин привязанного человека не меняет.
6. **Интерфейс** берёт режим из `/config.js`. `oidc` — `oidc-client-ts` (Authorization Code +
   PKCE, public client, токены в localStorage, продление по refresh). `proxy` — запросы с куками
   (`credentials: include`), при 401 — один POST на адрес продления на все упавшие запросы и
   повтор. На вход интерфейс сам не уводит, только кнопкой: провайдер может отказать и вернуть
   назад — автопереход зациклился бы. Код ошибки из адреса (`error`, `auth_error`) показывается.

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| Режим `ruto` с его SDK и ручкой `me` | меньше своего кода во фронте | zorko знает про ruto, другой шлюз не подойдёт | пользователь хочет, чтобы zorko не знал про ruto |
| В `proxy` всё же проверять подпись | защита при доступе в обход шлюза | нужен адрес ключей провайдера — это уже `oidc` | для этого есть `oidc`; `proxy` — именно доверие шлюзу |
| Общий секрет шлюза в заголовке | страховка от обхода шлюза | ещё один секрет | отклонено пользователем: API закрывается от прямого доступа |
| Проекты по ролям провайдера | всё в одном месте | роль на каждый проект, два списка вручную | провайдер не знает проектов zorko |
| Свои учётки и SSO одновременно | запасной вход | вторая дверь в `proxy`, сложнее | один режим на установку |

## Consequences
### Positive
- Один билд и один образ на все режимы: выбор — env.
- Админ и доступ отключаются у провайдера; роль снимается со следующим токеном.
### Negative
- Пустой список проектов больше не значит «все» — API-клиенты, заводившие людей без проектов,
  получат людей без доступа (интерфейс — галочка «Все проекты»).
- В `oidc` токены лежат в браузере (как свои в `local`).
### Risks
- **`proxy` верит любому токену.** API zorko (HTTP-шлюз и gRPC) должен быть доступен только через
  шлюз: без своего Ingress API, все ручки на шлюзе — с проверкой входа. При старте в лог пишется
  предупреждение.
- Привязка по логину верит логину провайдера: провайдер не должен давать людям самим менять
  `preferred_username` (в id.mdev.kz claims-идентификаторы не читают полей, которые человек
  заполняет сам).

## Dependencies
- ADR-005 (свои токены) остаётся для `local`.
