# ADR-001: Приём по протоколу Sentry на отдельном порту

**Status:** Accepted
**Date:** 2026-11-04
**Feature:** error-ingest
**Author:** 10x-Team (Architect + Staff Engineer)

## Context
Клиенты — веб, Flutter, React Native. Писать и сопровождать свои SDK для каждой платформы
дорого. Точка приёма публичная: её дёргают браузеры всех покупателей с любых доменов, ключ
виден в коде сайта. Админский API — внутренний, со своей будущей авторизацией (шаг 5).

## Decision
- zorko принимает протокол Sentry: `POST /api/{project_id}/envelope/` и `/store/`, ключ из
  `X-Sentry-Auth` / `sentry_key` / `dsn` заголовка envelope. Клиенты используют официальные SDK.
- Приём — отдельный `http.Server` на `INGEST_PORT` (не grpc-gateway), свой домен в ingress.
  CORS открыт для любых Origin; фильтрация сайтов — по `allowed_origin` ключа.
- Приём не ходит в базы на каждый запрос: ключи — в памяти (перечитка каждые 30 с),
  лимиты — «ведро жетонов» в памяти копии.

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| Свой протокол + свои SDK | полный контроль формата | SDK на 3+ платформы, переезд с Sentry болезненный | неподъёмно и бессмысленно |
| OpenTelemetry (OTLP) | стандарт, есть SDK | у OTel нет зрелой фронтовой модели ошибок (стек, breadcrumbs, релизы) | не решает задачу фронтендеров |
| Приём в общем grpc-gateway | один порт | лишний слой, общий CORS с админкой, спам бьёт по API | смешение публичного и внутреннего |

## Consequences
### Positive
- Готовые SDK и миграция с Sentry сменой DSN; приём масштабируется отдельно и не мешает админке.
### Negative
- Следуем чужому протоколу: изменения формата SDK нужно отслеживать.
### Risks
- Новая версия SDK меняет формат → тесты на образцах настоящих пачек всех платформ.
- Спам по публичному ключу → лимиты, `allowed_origin`, пределы размера.

## Dependencies
- Ограничивает шаг 3: загрузка карт должна быть совместима с `sentry-cli`/`@sentry/vite-plugin`.
