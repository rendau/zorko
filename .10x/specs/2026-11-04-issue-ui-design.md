# issue-ui — интерфейс: проблемы, события, проекты, вход

**Дата:** 2026-11-04
**Статус:** одобрено пользователем 2026-11-04
**Шаг дорожной карты:** 2 из 6 (см. `decisions/product-manager/_index.md`)

## Зачем

После шага 1 ошибки лежат в базах, но фронтендеры их не видят. Шаг 2 даёт им интерфейс уровня
Sentry для разбора ошибок, настройку проектов с готовым DSN и вход, чтобы интерфейс можно было
отдать людям, не дожидаясь шага 5.

## Входит / не входит

**Входит:** список проблем, карточка проблемы с событиями, проекты и ключи, люди; вход с ролями;
ручки сервера под эти экраны; раздача фронта Go-сервером.

**Не входит:** статусы «решено / отложено / вернулось», релизы как сущность, оповещения (шаг 4),
команды и доступ к отдельным проектам, TOTP, API-ключи (шаг 5), карты исходников (шаг 3),
автообновление списка, деплой.

## Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Экраны | список проблем, карточка проблемы, проекты (организации, проекты, ключи), люди |
| Поиск | строка как в Sentry (`key:value`) + выбор проекта, окружения, периода |
| Языки | русский (по умолчанию) и английский |
| Вход | сразу в шаге 2, **как в kusec**: JWT без похода в БД на каждый запрос, `jwts` не используется |
| Роли | админ (всё) и участник (смотрит проблемы и DSN) |
| Сборка фронта | **один бандл, без динамических подгрузок** |
| Раздача | **предсжатые `.br`/`.gz` как в ruto/kusec**; кэш в браузере **сутки** для файлов сборки, `index.html` — с проверкой при каждом открытии |

## 1. Экраны

Меню слева (`UDashboardSidebar`): выбор организации, «Проблемы», «Проекты», «Люди» (админ);
внизу — язык, профиль (смена имени и пароля), выход.

### Список проблем — `/issues`
- Фильтры (в URL query): проекты (по умолчанию все проекты организации), окружение, период
  `1h | 24h | 7d | 14d | 30d` (по умолчанию `14d`), строка поиска `q`, сортировка `sort`.
- Строка поиска: язык из раздела 3; подсказки ключей (`/tag/key`) и значений (`/tag/value`) при наборе.
- Строка списка: метка уровня, заголовок, место падения, проект, «впервые … · последний раз …»
  (абсолютные даты — в подсказке), мини-график событий за период (24 столбика), события и люди
  за период.
- Сортировка: `last_seen` (по умолчанию), `first_seen`, `events`, `users`.
- Страницы по 25; пустое состояние — подсказка подключить SDK со ссылкой на ключи проекта.
- Кнопка «обновить» и время загрузки данных.

### Карточка проблемы — `/issues/:id`
- Шапка: заголовок, место падения, уровень, проект, платформа; всего раз (`times_seen`), людей за
  период, «впервые» и «последний раз» с релизами (`first_release`, `last_release`).
- График: по часам (24h) или по дням (30d).
- Теги: топ-5 значений по ключам с процентами; клик по значению фильтрует события проблемы.
- Событие (по умолчанию последнее), кнопки «первое / раньше / позже / последнее», id и время:
  - исключения цепочки: тип, текст, механизм (`handled`), кадры — свои раскрыты, кадры библиотек
    свёрнуты; строки исходника (`pre_context`/`context_line`/`post_context`), если пришли;
  - «что было перед ошибкой» (breadcrumbs): категория, сообщение, данные, уровень, время
    относительно ошибки;
  - теги события; контекст: браузер, ОС, устройство, runtime, приложение, пользователь, запрос
    (url, метод, заголовки), SDK; `extra`;
  - сырой JSON с копированием.
- Вкладка «События»: таблица сохранённых событий (время, релиз, браузер, ОС, пользователь,
  страница), фильтр строкой поиска, страницы по 50; пояснение «счётчик — все падения, в списке —
  сохранённые подробно (до 100 в минуту)».

### Проекты — `/settings`
- Организации: список, создать, переименовать, удалить с подтверждением (админ).
- Проекты организации: slug, название, платформа; создать, изменить, удалить с подтверждением.
- Ключи проекта: метка, вкл/выкл, лимит в секунду, разрешённые сайты; DSN с копированием; код
  подключения для Vue, React, браузера (script), Flutter, React Native — с подставленным DSN.
- Участник видит всё, но без кнопок изменения.

### Люди — `/users` (админ)
- Список: имя, логин, роль, активен. Создать с временным паролем, сменить роль, отключить,
  задать новый пароль, удалить.

### Вход — `/login`, первый запуск — `/setup`
- `/setup` доступен, только пока в системе нет ни одного человека (`BootstrapStatus`).

## 2. Ручки сервера

Все — gRPC + HTTP-шлюз, пути в единственном числе, пагинация с 0, int64 строками (protojson).
Все требуют вход, кроме `POST /usr/login`, `POST /usr/token/refresh`, `GET /usr/bootstrap/status`
и создания первого админа (`POST /usr`, пока людей нет).

### Проблемы и события
| RPC | HTTP | Что |
|---|---|---|
| `IssueService.List` | `GET /issue` | `org_id`, `project_ids[]`, `environment`, `period`, `q`, `sort`, `list_params` → строки: проблема + `events`, `users` за период + `sparkline[24]` |
| `IssueService.Get` | `GET /issue/{id}` | проблема + `events`, `users` за `period` |
| `IssueService.Stat` | `GET /issue/{id}/stat` | `period`, `interval` (`hour` / `day`), `environment` → ряд `{ts, count}` |
| `IssueService.Tags` | `GET /issue/{id}/tag` | `period`, `environment` → по ключам: всего, топ-5 `{value, count}` |
| `EventService.List` | `GET /event` | `issue_id`, `q`, `period`, `list_params` → сохранённые события (сводка без `data`) |
| `EventService.Get` | `GET /event/{event_id}` | `issue_id` → событие + `data` (JSON строкой) + `prev_event_id`, `next_event_id`; `event_id` = `latest` / `oldest` — последнее / первое |
| `TagService.Keys` | `GET /tag/key` | `org_id`, `project_ids[]`, `period` → ключи тегов (до 100, по частоте) |
| `TagService.Values` | `GET /tag/value` | `key`, `prefix`, те же фильтры → до 20 значений по частоте |

### Как строится список (`IssueService.List`)
1. Слова поиска без ключа → `issue.id` из Postgres по `title`/`culprit` `ILIKE` в проектах
   фильтра (до 5000).
2. ClickHouse, `event_stat`: `project_id in (…)`, `timestamp >= now − period`, окружение, условия
   тегов, `issue_id in (…)` из п. 1 → `group by issue_id`: `count()`, `uniqIf(user_key, user_key != '')`,
   `max(timestamp)`. Не больше 50 000 проблем (предел — в ответе флаг `truncated`).
3. Postgres: строки `issue` по найденным id → сортировка (`last_seen`/`first_seen` — из PG,
   `events`/`users` — из п. 2) и страница в Go.
4. ClickHouse: мини-графики только для `issue_id` страницы (24 интервала периода).

Точность до слияния частей ClickHouse — как в ADR-003 (редкие повторы пачек).

### Пользователи (как в kusec)
| RPC | HTTP | Кто |
|---|---|---|
| `UsrService.Login` | `POST /usr/login` | все → `{jwt, refresh_token}` |
| `UsrService.RefreshToken` | `POST /usr/token/refresh` | все (по refresh-токену) |
| `UsrService.BootstrapStatus` | `GET /usr/bootstrap/status` | все → `{bootstrap_required}` |
| `UsrService.GetProfile` / `UpdateProfile` | `GET` / `PUT /usr/profile` | вошедший (имя, логин, пароль) |
| `UsrService.List` / `Get` | `GET /usr`, `GET /usr/{id}` | вошедший |
| `UsrService.Create` | `POST /usr` | админ; без входа — только пока людей нет (первый — админ) |
| `UsrService.Update` / `Delete` | `PUT` / `DELETE /usr/{id}` | админ (себя удалить и снять с себя админа нельзя) |

Права в существующих ручках: `List`/`Get` у `org`, `project`, `project_key` — вошедший;
`Create`/`Update`/`Delete` — админ.

## 3. Язык поиска

- `key:value` — тег равен значению; `key:"с пробелом"` — значение в кавычках.
- `!key:value` — тег не равен.
- `key:*часть*`, `key:начало*` — содержит / начинается (в `value` `*` → `%` для `LIKE`).
- Слово без ключа — поиск по заголовку и месту падения проблемы (`ILIKE`, все слова — «и»).
- Ключи — теги `event_stat.tags` (`level`, `environment`, `release`, `browser`, `browser.name`,
  `os`, `os.name`, `device`, `runtime`, `url`, `transaction`, `handled`, `mechanism`, `user`, теги SDK).
  `environment` из строки складывается с выбором окружения.
- Несколько условий — «и». Неизвестный синтаксис (например, незакрытая кавычка) — отказ
  `invalid_query` с позицией ошибки.
- Разбор — Go-пакет с табличными тестами; в ClickHouse условия уходят только параметрами.

## 4. Вход — как в kusec

- Таблица `usr`: `id`, `created_at`, `modified_at`, `active`, `is_admin`, `name`, `username`
  (уникальный), `password` (bcrypt). Пароль — от 8 до 72 байт (bcrypt молча обрезает длиннее).
- `JWT_SECRET` (HS256). Access-токен — 15 минут: `typ=access`, `id`, `is_admin`, `iat`, `exp`;
  проверяется только подпись и срок, **без БД**. Refresh-токен — 30 дней: `typ=refresh`, `id`,
  `pwd` (отпечаток хеша пароля), `iat`, `exp`; при обмене пользователь перечитывается из БД
  (активен, роль), смена пароля отзывает все refresh-токены.
- gRPC-перехватчик: `authorization: Bearer <jwt>` → сессия `{Id, Admin}` в контексте; usecase
  проверяет `CtxIsAuthorized` / `CtxIsAdmin` (отказы `not_authorized`, `no_permission`).
- Перебор паролей: не больше 5 неудачных входов в минуту на логин и на IP (`service/ratelimit`).
- Фронт: токены в `localStorage`; при 401 — один раз `token/refresh` и повтор запроса, при
  неудаче — `/login?redirect=…`.
- Новые env: `JWT_SECRET` (в kusec — генерацией).

## 5. Фронт

- `admin/`: Nuxt 4 + Nuxt UI 4, `ssr: false`, раскладка и соглашения planora (`pages`, `layouts`,
  `components`, `composables` — `useApiAction`, `useQueryFilters`, `useAuth`; `api/*.api.ts`
  поверх `apiFetch`; `types/*`; `utils/*`).
- **Один бандл:** `vite.build.rollupOptions.output.inlineDynamicImports = true`,
  `cssCodeSplit = false`, без `Lazy*`-компонентов и асинхронных импортов. Если Nuxt 4 так не
  собирается — переход на Nuxt UI поверх Vite + Vue (как kusec), с предупреждением пользователя.
- Иконки (`@iconify-json/lucide`, `provider: 'none'`) и шрифты — только из сборки.
- i18n ru/en: ключи по пространствам (`common.*`, `nav.*`, `apiError.<code>`, `<страница>.*`);
  `scripts/check-locales.mjs` и `scripts/check-raw-text.mjs` по образцу planora.
- Графики — свои SVG-компоненты (столбики во времени, полосы распределения тегов).
- Вид: плотный, `primary: violet`, `neutral: zinc`, тёмная тема по системе; узкий экран — шапка
  переносится, таблицы — `overflow-x-auto`.
- Событие рисуется из исходного JSON Sentry (`exception.values`, `breadcrumbs.values`, `contexts`,
  `request`, `extra`, `tags`, `user`, `sdk`) — разбор в `utils/event.ts` с тестами (`node --test`).

## 6. Раздача фронта Go-сервером

- Отдельный порт `ADMIN_PORT` (по умолчанию 8001), каталог `ADMIN_DIR` (по умолчанию
  `./admin-ui`); каталога нет — сервер не поднимается (warn в лог).
- `/config.js` → `window.__APP_CONFIG__ = {apiBaseUrl: ADMIN_API_BASE_URL}`, `no-store`.
- Файл есть → он; иначе → `index.html` (адреса SPA).
- Сжатие как в ruto/kusec: `admin/scripts/compress.mjs` пишет `.br` (качество 11) и `.gz`
  (уровень 9) рядом с текстовыми файлами сборки; Go отдаёт копию по `Accept-Encoding`
  (`br` предпочтительнее), `Content-Type` и `Last-Modified` — от оригинала, `Vary: Accept-Encoding`;
  на лету не сжимает.
- Кэш: файлы сборки — `Cache-Control: public, max-age=86400`; `index.html` и адреса SPA —
  `no-cache` (проверка `Last-Modified` → `304`), чтобы новый релиз виден сразу; в имени бандла —
  хеш содержимого.
- Сборка: `make build-admin` (`pnpm generate` → `compress.mjs` → `admin-ui/`), Dockerfile копирует
  `admin-ui/`.
- Новые env: `ADMIN_PORT`, `ADMIN_DIR`, `ADMIN_API_BASE_URL`. Для фронта на другом домене —
  `HTTP_CORS=true` у шлюза (причина есть: SPA и API на разных хостах).

## 7. Проверка

- Go (testify): разбор поиска; сессии (подпись, срок, тип токена, отпечаток пароля); usecase
  `usr` (первый админ, права, перебор); права в `org`/`project`/`project_key`; раздача статики
  (выбор `.br`/`.gz`/оригинала, кэш, SPA-fallback, `config.js`).
- Интеграционные на стенде: `IssueService` (список, сортировки, фильтры тегов и слова, период,
  мини-графики), `Stat`, `Tags`, `EventService` (страницы, соседи, `latest`/`oldest`), `TagService`.
- Фронт: `typecheck`, `lint`, `check:i18n`, `node --test` для `utils/event.ts`; проверка, что в
  сборке ровно один JS и один CSS и у них есть `.br`/`.gz`.
- Вживую через Chrome (Claude-in-Chrome): первый админ → вход → наполнение стенда (`loadgen` +
  браузерная страница) → список, поиск `browser.name:Chrome`, сортировки, период → карточка
  (стек, breadcrumbs, теги, «раньше / позже», сырой JSON) → проекты и ключи (DSN, код
  подключения) → участник без кнопок изменения и с отказом сервера → истечение access-токена и
  незаметное обновление → ru/en. Заголовки ответа статики: `Content-Encoding: br`, кэш.
- Узкие экраны — прогон `frontend-visual-qa` (Level C) по ширинам.

## 8. Порядок работы

1. Вход и люди: `usr`, сессии, перехватчик, права в существующих ручках.
2. Ручки проблем, событий и тегов, язык поиска.
3. Фронт целиком + раздача статики.

Ветка — master (решение пользователя для проекта), коммиты по задачам.

## Критерии готовности

1. Админ создаётся на `/setup`, заводит участника; участник входит и видит проблемы и DSN, но не
   может ничего изменить (ни кнопок, ни ответа сервера).
2. Все проверки раздела 7 проходят.
3. Сборка фронта — один JS и один CSS, отдаются сжатыми, с кэшем на сутки; `index.html` — с проверкой.
